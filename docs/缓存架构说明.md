# RxyCode 缓存架构说明

## 概览

RxyCode 采用**三级缓存架构**，从应用层到 LLM 服务层逐级优化响应速度和 token 成本：

```
用户请求
  │
  ├─ Level 1: 精确缓存 (PreciseCache)     ── hash 精确匹配，0 延迟
  │
  ├─ Level 2: 语义缓存 (SemanticCache)     ── 文本相似度匹配，近似命中
  │
  └─ Level 3: LLM Provider KV Cache        ── 服务端上下文缓存，降低 token 费用
```

---

## Level 1: 精确缓存 (PreciseCache)

**文件**: `cache/precise_cache.py`

### 原理

对请求做 **SHA-256 哈希**，完全相同的请求直接返回缓存结果，零 LLM 调用。

### Cache Key 生成

```
system_hash = sha256(长度前缀(namespace, 完整system_prompt))
query_hash = sha256(长度前缀(query的原始UTF-8字节))
key = system_hash + ":" + query_hash + ":" + tool_hash + ":" + prompt_version_hash
```

- **System Prompt 指纹**: 使用完整提示词，避免不同提示词共享相同前缀时发生污染
- **模型命名空间**: 由 provider endpoint、model_name 和 credential 摘要组成，隔离不同模型与租户的回答
- **Query 精确匹配**: 不裁剪、不折叠空格、不移除填充词或标点、不转换大小写、不做 Unicode 归一化；任一 UTF-8 字节不同都会生成不同 key
- **分量边界**: 各分量使用长度前缀编码，避免 namespace、system prompt 或 tool 参数中的分隔符造成碰撞
- **Tool 指纹**: 缓存 API 保留可选 tool_name/tool_args，但工具感知 Agent 路径不会读写应用答案缓存

### 特性

| 属性 | 值 |
|------|-----|
| 存储方式 | 原子替换 JSON 文件 (`~/.rxycode/cache/precise_index.json`) |
| 默认 TTL | 7200 秒（2 小时） |
| 匹配精度 | 100%（完全相同的请求） |
| 工具感知 Agent 路径 | 禁用应用答案缓存 |

### 核心逻辑

```python
namespace = f"{provider_endpoint}|{model_name}"

# 读取
cached = precise_cache.get(system_prompt, query, namespace=namespace)
if cached:
    return cached["response"]  # 直接返回，跳过 LLM

# 写入（LLM 响应后）
precise_cache.put(system_prompt, query, answer, namespace=namespace)
```

## Level 2: 语义缓存 (SemanticCache)

**文件**: `cache/semantic_cache.py`

### 原理

使用 **两阶段匹配**，对措辞不同但意图相同的请求返回缓存结果：

1. **Stage 1 - 字符串相似度**: `SequenceMatcher.ratio() >= 0.95`（近乎重复）
2. **Stage 2 - 实体重叠度**: 关键实体 token 重叠率 `>= 0.60`（防止不同主题误匹配）

### 实体提取

从查询中提取有意义的关键词：
- 英文单词（3+ 字符）
- 中文片段（2+ 字符连续 CJK）
- 数字和引号内容

去除停用词（中英文各 100+ 个）后计算交集比例。

### 防误匹配设计

阈值从 0.80 提升至 **0.95**，确保只有近乎重复的查询才会命中。例如：

```
"Python 怎么排序列表"  vs  "JavaScript 怎么排序数组"
→ 相似度高，但实体不同 → 不命中 ✓
```

### 特性

| 属性 | 值 |
|------|-----|
| 存储方式 | 原子替换 JSON 文件 (`~/.rxycode/cache/semantic_index.json`) |
| 默认 TTL | 7200 秒（2 小时） |
| 最大条目 | 500（超出后保留命中最多的 300 条） |
| 过期处理 | 相似度扫描前清理全部过期条目 |
| 模型隔离 | provider endpoint/model_name 命名空间 |
| 过滤错误响应 | 是（不缓存 "不知道"、"找不到" 等） |
| 最短响应 | 10 字符以上才缓存 |

### JSON 持久化与损坏恢复

`cache/json_store.py` 为两个应用缓存提供相同的持久化协议：同一路径的操作共享进程级可重入锁，修改前在锁内重新加载最新索引，写入同目录临时文件并 `flush`/`fsync` 后通过 `os.replace` 原子替换。这样多个线程或多个缓存实例不会互相覆盖更新，读者也不会看到半写入 JSON。

JSON 截断、根类型错误或条目结构错误时，原文件会保留为 `<index>.corrupt-<timestamp>`，并立即重建为空的有效索引。

## Level 3: LLM Provider KV Cache

**文件**: `cache/prompt_cache.py`, `core/prompts.py`, `core/agent_v2.py`

### 原理

利用 DeepSeek / OpenAI 的 **服务端上下文缓存**（Prompt Cache），避免重复处理相同的前缀 token。

### 关键设计

1. **统一 System Prompt**: 所有 LLM 调用（fast path、5 个 graph node、子 agent）使用**完全相同的 system prompt**，节点特定指令放在 user message 中 → 100% system prompt 缓存命中
2. **固定前缀顺序**: system → tools → history → new_input，只追加不修改
3. **无动态内容**: 前缀中不注入时间戳等动态信息

### 缓存命中 Token 提取

`_extract_cache_read()` 函数兼容三种 LLM 响应格式：

| Provider | 字段路径 |
|----------|---------|
| DeepSeek | `response_metadata.token_usage.prompt_cache_hit_tokens` |
| OpenAI | `response_metadata.usage.prompt_tokens_details.cached_tokens` |
| LangChain 标准 | `usage_metadata.input_token_details.cache_read` |

### 统计追踪

`TokenStats` 类（`utils/streaming.py`）实时追踪：

```python
token_stats.add_real_usage(
    input_tokens=...,      # 总 prompt token 数
    output_tokens=...,     # 输出 token 数
    cache_read_tokens=...  # 命中 provider 缓存的 token 数
)
```

Provider 前缀缓存命中率计算：`cache_hit_tokens / prompt_tokens * 100`。

应用答案缓存按 `precise`、`semantic` 分层记录 `requests`、`eligible`、`bypassed`、`hits` 和 `misses`。`hit_rate`/`miss_rate` 以 eligible lookup 为分母，`eligibility_rate`/`bypass_rate` 以该层 requests 为分母，不与 provider token 缓存指标混算。`GET /status` 和 `/cache` 分别通过 `application_cache` 与 `provider_cache` 暴露两套指标。

## 调用流程

```
用户输入
  │
  ▼
_fast_reply()
  │
  ├─ 构建 cache_key = JSON数组(query, 完整memory_ctx的SHA-256摘要或null)
  ├─ 构建 namespace = provider_endpoint + model_name + credential摘要
  │
  ├─ PreciseCache.get(..., namespace) ── 命中 → 直接返回（跳过 LLM）
  │
  ├─ SemanticCache.get(..., namespace) ── 命中 → 直接返回（跳过 LLM）
  │
  └─ 缓存未命中 → LLM 调用
       │
       ├─ 统一 prompt registry 构建 messages（保证前缀稳定）
       │
       ├─ LLM 响应 → _extract_cache_read() 提取 provider 缓存命中
       │
       ├─ PreciseCache.put(..., namespace) 存储精确缓存
       │
       └─ SemanticCache.put(..., namespace) 存储语义缓存（仅无 memory_ctx 时）

_fast_reply_with_tools()
  └─ 始终绕过 PreciseCache/SemanticCache，避免复用外部状态或副作用结果
```

## 管理命令

| 命令 | 功能 |
|------|------|
| `/cache` | 查看精确缓存和语义缓存的统计信息 |
| `/cache clear` | 清空所有应用层缓存 |
| `/cache clean` | 清除已过期的缓存条目 |

## 文件结构

```
cache/
├── __init__.py
├── precise_cache.py      # Level 1: 精确哈希缓存
├── semantic_cache.py     # Level 2: 语义相似度缓存
├── json_store.py         # JSON 原子写入、线程锁与损坏恢复
└── text_normalizer.py    # 语义匹配可用的文本归一化工具

~/.rxycode/cache/         # 运行时缓存数据
├── precise_index.json    # 精确缓存索引
└── semantic_index.json   # 语义缓存索引
```
